# Email Notification System Implementation Plan

## Overview
Implement an asynchronous email notification system for the PMC system using Django + Celery + Redis. The system will handle notifications for project assignments and DPR (Detailed Project Report) workflow events.

## Current System Analysis
- **Project Model**: Uses ManyToManyField `assigned_users` for assignments, not single `assigned_to`
- **DPR Model**: Uses `submitted_by` (not `created_by`), `approved_by`, `rejected_by`
- **User Model**: Default Django User with extended UserProfile
- **No existing email system**

## Required Changes & Implementation

### 1. Dependencies & Configuration
- Add Celery and Redis to `requirements.txt`
- Configure Celery settings in Django settings
- Set up email backend configuration (SMTP)
- Add environment variables for email credentials

### 2. Email Templates
Create HTML email templates in `templates/emails/`:
- `project_assigned.html`
- `dpr_submitted.html` 
- `dpr_approved.html`
- `dpr_rejected.html`

Each template should include:
- User name, project name, DPR title, status, rejection reason

### 3. Core Components

#### Models (Optional)
Create `Notification` model for logging:
```python
class Notification(models.Model):
    user = models.ForeignKey(User, ...)
    message = models.TextField()
    type = models.CharField(...)  # project_assigned, dpr_submitted, etc.
    is_read = models.BooleanField(default=False)
    created_at = models.DateTimeField(auto_now_add=True)
```

#### Email Utility (`utils/email.py`)
- Reusable function to send HTML emails
- Template rendering with context
- Error handling

#### Celery Tasks (`tasks.py`)
- `send_notification_email` task with retry mechanism
- Async execution to not block API responses

#### Notification Service (`services/notifications.py`)
Functions:
- `notify_project_assigned(project, assigned_user)`
- `notify_dpr_submitted(dpr)`
- `notify_dpr_approved(dpr)`
- `notify_dpr_rejected(dpr)`

### 4. Business Logic Integration
- **Project Assignment**: Hook into project assignment logic (when user added to assigned_users)
- **DPR Events**: 
  - Submit: In DPR submit view
  - Approve: In DPR approve views
  - Reject: In DPR reject view

### 5. Receiver Logic Clarification Needed
Current model fields don't exactly match requirements:
- Project: `assigned_users` (ManyToMany) vs `assigned_to` (single)
- DPR: `submitted_by` vs `created_by`
- Need to clarify: Who receives DPR submitted emails? (current_approver_role logic?)
